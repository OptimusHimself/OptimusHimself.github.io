3. Root 与安全状态 ★核心发现

属性 值 含义

ro.boot.flash.locked (空) —

关键结论

  1. adb root 不可用。LineageOS 官方构建即使打着 userdebug 标签，也会刻意将
    ro.debuggable 置为 0。这与 AOSP 原生 userdebug 的默认行为不同——不要假设
    ro.build.type=userdebug 就等于 adb root 可用。

  2. BL 已解锁（verifiedbootstate=orange）。这是 root 流程中风险最高的一步
    （解锁会清空全盘数据），而该设备已跨过此门槛。意味着后续上 Magisk 无需再次
    擦除数据    。

  3. SELinux 为 Enforcing，root 后需处理策略，但 Magisk 会在 permissive 域内注入。

5. 对 process-prober 的能力边界结论

当前身份为 shell（uid 2000），在 Android 16 + Enforcing 下：

无需 root 即可采集

手段 可获取
ps -A 全量进程列表（PID / USER / NAME / RSS）
dumpsys activity processes 进程 adj、oom_adj、状态、前台/后台
dumpsys meminfo 单进程内存明细
dumpsys procstats 历史进程统计
top 实时 CPU 占用
getprop / dumpsys package 系统与包元数据

必须 root 才能采集

目标 受阻原因
其他应用 /proc/<pid>/cmdline SELinux 域隔离
/proc/<pid>/maps、environ SELinux proc_* 标签限制
/proc/<pid>/stat、status 详情 同上
其他应用数据目录 文件权限 + SELinux

结论：枚举进程 + 元数据可在纯 shell 下完成；读取原始 /proc 内容必须 root。

6. 后续路线

路线 A — Magisk root（推荐，成本最低）

前置条件已满足：BL 已解锁，无需擦数据。

  1. 从已刷入的 LOS nightly 包中提取 boot.img / init_boot.img
  2. Magisk App 打补丁 → 生成 magisk_patched-*.img
  3. fastboot flash init_boot magisk_patched-*.img
  4. 重启，adb shell su 验证

路线 B — KernelSU

需内核支持。LOS 官方内核大概率不含 KernelSU 补丁，需自行编译内核（GKI 设备可走
GKI 替换路线）。成本高于 Magisk。

路线 C — 自编译 LOS（ro.debuggable=1）

本地已有 los-playground 目录。若后续要长期做底层开发，可自编译带
ro.debuggable=1 的构建，从而启用 adb root，省去 Magisk 的注入层。
代价：源码 ~200GB + 数小时编译。

路线 D — 纯 shell（零改动）

若 prober 仅需进程枚举与 dumpsys 元数据，可直接开始，无需任何 root 操作。
